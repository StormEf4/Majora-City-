# Majora City: Roadmap

Status legend: ✅ done · 🧪 code complete, needs in-game tuning · 🚧 in progress · ⬜ planned

The roadmap is ordered so that **every milestone ends with a playable ROM**. Early milestones build the systems
and the vertical slice; later ones fill the city with content. Design details live in [`docs/design/`](docs/design).

---

## M0 · Foundation ✅

- ✅ Project vision, story bible, world, cast, mechanics, masks and side-mission design docs
- ✅ Pinned decompilation base ([zeldaret/mm](https://github.com/zeldaret/mm), see `decomp.lock`)
- ✅ Overlay workflow: `mod/` (new files) + `patches/` (diffs to decomp files) → `tools/apply.sh`
- ✅ Build, check (no ROM needed; includes an IDO 7.1 compile), and BPS patch tooling (`tools/build.sh`,
  `tools/check.sh`, `tools/bps.py`, cross-checked against an independent BPS implementation)
- ✅ Core module `mc_core.c`: story/cycle flags, scene-augmentation spawner, cycle-reset hook
- ✅ Majora City save block (`McSaveData`, 84 bytes) placed in the unused `SaveInfo.unk_DF4` region, so the save size is unchanged
- ✅ Custom text bank (`mod/assets/text/mc_message_data.h`, IDs `0x4D00`+)

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Decomp churn breaks our patches | The base is pinned in `decomp.lock`; we rebase deliberately, one bump per milestone. |
| Parts of the ROM aren't fully shiftable | Prefer new overlays over growing `code`; keep `code` additions small (`mc_core.c` only). |
| RAM / polygon budget on N64 | Procedural skyline uses a single 32×32 texture and about 20 triangles per tower (200 in Termina Field); budgets in [architecture.md](docs/tech/architecture.md). |
| Save-format compatibility | All new persistent data fits inside the 84-byte unused `unk_DF4` block; a static assert guards the size. |
| Legal | No ROM, assets, or extracted data are ever committed. Players apply a BPS patch to their own dump. |
